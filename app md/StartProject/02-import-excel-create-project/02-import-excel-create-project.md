## Title
Start a project — Import from Excel: confirm and create the project

### Summary
Once a workbook has been checked and passed validation (no `error`-severity issues), clicking "Create project" turns the previously-staged `ImportBatch` into a real `Project` + `ProjectVersion 1` plus all of its trades, bidders, trade partners, zones, crew, and base-requirement scope lines in one transaction, then takes the user straight into the new project's Bid board.

### User story
As an estimator who has uploaded and reviewed a filled template, I want one click to turn that reviewed workbook into a fully-populated project, so that I don't have to re-enter trades, bidders, zones, crew or scope by hand.

### Acceptance criteria
- [ ] The "Create project" button is enabled only once `check.ok` is true and calls `create()`, which in import mode posts to `/api/imports/{check.token}/create` with no body.
- [ ] On success the modal closes and the app navigates to `/p/{projectNo}/v/{versionNo}/bid-board` for the newly created project/version (`onCreated(projectNo, versionNo)` in `Portfolio.tsx`), and the Portfolio project list is refetched so the new project appears immediately.
- [ ] Only the user who uploaded the workbook can create from it — a different user hitting the same token gets `403 Forbidden` ("Only the person who uploaded this workbook can create from it.").
- [ ] Creating twice from the same token is blocked: a batch already `Status = 'created'` returns `409` ("This workbook was already imported.", code `duplicate").
- [ ] A batch that never passed validation (`Status != 'checked'`) returns `400` ("Fix the problems in the workbook and upload it again.").
- [ ] If the stored workbook still re-parses with errors at create time (re-validated from the saved file, not trusted from the earlier check), the request fails with `400` ("The workbook has problems. Upload it again to see them.") rather than creating a partial project.
- [ ] A successful create populates, from the workbook: the `Project` row and `ProjectVersion` 1 (auto-numbered if the workbook left "Project number" blank, or using the workbook's number if free), version markups (fee/contingency/builders-risk rates from the sheet), `Zone` rows (and sets `GrossArea`/`ZonesSetArea` from zone areas when the workbook didn't give a gross SF), a dedicated `RequirementSet`/`RequirementLine` set when the workbook included its own Requirements sheet, one `Trade` per workbook trade row (CSI code matched to a current `WorkCode`, scope kit matched to `ScopeKit` by name), one `TradePartner`/`PartnerPerson`/`Bid` per bidder row (new partners auto-created, matched by company name), `TradeZone` splits (from the sheet or each zone's default share), base-requirement/zone/trade-kit `ScopeLine` rows per trade, `ProjectWeek`/`TeamMember`/`TeamMemberWeek` rows when the workbook included a Crew sheet, and the version's default cost kit lines (precon/overhead `CostLine` rows).
- [ ] The response includes `tradesAdded`, `tradesUpdated` (always 0 for a new project), `bidsAdded`, `partnersAdded`, and `ms` (elapsed import time) in addition to `projectId/projectNo/versionId/versionNo`.
- [ ] Requires the `import.run` capability (same check as the upload/check step).

### Technical spec
**Frontend:** `web/src/pages/StartProject.tsx`, `create()` handler: `mode === 'import' ? await api.post<{ projectNo: string; versionNo: number }>('/imports/' + check!.token + '/create') : ...`. Button is disabled while `busy`. Errors are caught and rendered in the same `role="alert"` paragraph as the check step. `Portfolio.tsx` supplies `onCreated={(no, v) => { refetch(); nav('/p/' + no + '/v/' + v + '/bid-board') }}`.
**Backend:** `POST /api/imports/{token:guid}/create` in `ImportEndpoints.Map` (`api/src/Gridline.Api/Endpoints/ImportEndpoints.cs`). Requires capability `import.run`. Looks up the `ImportBatch` by `PublicKey = @token` `FOR UPDATE` (row-locked for the duration of the transaction), checks ownership (`StartedBy == w.User.UserId`), `Status` state machine (`created` → 409, not `checked` → 400), re-reads the saved file from `Storage` (`imports/{token}.xlsx`) and re-parses with `Template.Read(..., tradesOnly: false)`, re-checking `ErrorCount`. Delegates to `ImportService.CreateProject(w, m)` (`api/src/Gridline.Api/Import/ImportService.cs`), which: builds a `ProjectEndpoints.ProjectIn` from the parsed sheet, calls the shared `ProjectEndpoints.CreateProject(w, p)` (see ticket 03 for that routine's own inserts), then applies version markup overrides (fee/contingency/builders-risk), inserts `Zone` rows and recomputes gross area/`ZonesSetArea`, optionally creates a project-specific `RequirementSet`, bulk-loads Trades/Bidders/zone-splits/Requirements via Postgres binary `COPY` into temp tables (`imptrade`, `impbid`, `impsplit`, `impreq`) for set-based inserts into `Trade`/`TradePartner`/`PartnerPerson`/`Bid`/`TradeZone`/`ScopeLine`, loads `Crew` into `ProjectWeek`/`TeamMember`/`TeamMemberWeek`, applies the default `CostKit`/`CostKitItem` set via `ProjectEndpoints.ApplyDefaultCostKits`, and finally calls `Recalc.VersionBulk(w, vid, "import.create")` (see Architecture.md: Recalculation engine). After the service call, the endpoint updates `ImportBatch.Status = 'created'` with `TargetProjectId`/`TargetVersionId`/`FinishedAt`, logs one `ActivityEvent` via `w.Log(projectId, versionId, "import.create", "import", batchId, after: {tradesAdded, tradesUpdated, bidsAdded, partnersAdded, ms})`, and commits (`w.Commit()` both commits the transaction and broadcasts a SignalR `changed` event to the new project's group — see Architecture.md: Unit of work).
**Database:** Writes (all in `db/migrations/001_init.sql` unless noted): `ImportBatch` (status transition to `'created'`, `TargetProjectId`/`TargetVersionId` FKs with `ON DELETE SET NULL`), `Project`, `ProjectVersion` (`UNIQUE (ProjectId, VersionNo)`, partial unique index `UxOnePrimaryVersion` on `IsPrimary`), `VersionMarkup` (`PRIMARY KEY (VersionId, MarkupCode)`), `ProjectMember` (`PRIMARY KEY (ProjectId, UserId)`), `RecentProject` (`PRIMARY KEY (UserId, ProjectId)`), `Zone` (`UNIQUE (VersionId, ZoneCode)`), `RequirementSet`/`RequirementLine`, `Trade` (`CsiCode`, `ScopeNo`, denormalized `ProjectId` set by trigger `TrgTradeProject BEFORE INSERT OR UPDATE OF VersionId ON Trade`), `TradePartner` (dedup via `ON CONFLICT ((lower(CompanyName))) DO NOTHING`), `PartnerPerson`, `Bid` (denormalized `ProjectId`... actually `TradeId`-derived via trigger `TrgBidProject BEFORE INSERT OR UPDATE OF TradeId ON Bid`), `TradeZone`, `ScopeLine`, `ProjectWeek`/`TeamMember`/`TeamMemberWeek`, `CostLine`. `TrgTouch` triggers (on `Project`, `ProjectVersion`, `Trade`, `Bid`, `TradePartner`, `ScopeLine`, `CostLine`, `TeamMember`) only fire on `UPDATE`, not the `INSERT`s this flow mostly performs, except the `Trade`/`TradePartner` budget/note `UPDATE`s in the "into existing version" path (not used here since `newProject: true`). `CompanyProfile.NextProjectNo` is incremented when the workbook left the project number blank (`UPDATE CompanyProfile SET NextProjectNo = NextProjectNo + 1 RETURNING ProjectNoPrefix || (NextProjectNo - 1)`).

- Shares `ProjectEndpoints.CreateProject` with `03-start-blank-project.md` — a change to one affects the other's project/version/markup/member bootstrap.
- See `_Overview/Architecture.md`: Unit of work (`Work`/`Access`/SignalR `changed` broadcast), Recalculation engine (`Recalc.VersionBulk`), Import/Export.

### Notes / edge cases
- The create step re-parses the saved `.xlsx` from disk rather than trusting the earlier check response — if the underlying file changed or storage is unavailable between check and create, this step is the one that fails, not the check step.
- Because `Access.Version` is never called for the new-project path, there is no version-locked (`423`) concern here — the version doesn't exist until this call creates it.
- The newly created project has exactly one `ProjectMember` (the creator, as `'owner'`) plus the workbook's matched Estimator/Manager (as `'editor'`) if found; no other user is in the project's SignalR group yet, so the `changed`/`import.create` broadcast effectively has no other tab listening until someone else opens the project.
- `TradesUpdated` is always `0` from this endpoint (only the "trades into an existing version" variant updates existing trades); don't assume it reflects anything about the new project.
- Large workbooks are handled via `COPY ... FORMAT BINARY` into temp tables rather than row-by-row inserts — this is why one request can create a 100+ trade project quickly, but also means a mid-import SQL error rolls back everything (`Work`'s single transaction), leaving no partial project.
