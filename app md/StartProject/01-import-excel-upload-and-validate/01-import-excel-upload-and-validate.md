## Title
Start a project — Import from Excel: upload and validate the workbook

### Summary
In the "Start a project" modal's default "Import from Excel" mode, the user downloads the blank template, fills it in offline, then drags/drops or browses to a filled `.xlsx` workbook. The workbook is uploaded and server-validated (sheet shape, CSI/state/user cross-references) without writing any project data, and the user sees a preview of what will be created: project header, sheet row counts, per-trade budget/bidder/match info, validation issues, and trade-partner matching stats.

### User story
As an estimator starting a new project from a filled-in Excel template, I want to upload the workbook and see a validation preview before anything is created, so that I can fix problems in the workbook (or decide to proceed) without risking a half-created project.

### Acceptance criteria
- [ ] The modal opens in `mode === 'import'` by default, with a segmented control to switch to "Start blank" (`StartProject.tsx` `mode` state).
- [ ] A "Download template" link (`href="/api/template.xlsx"`) is always visible in the drop zone before a file is checked; it is an anonymous `GET /api/template.xlsx` that serves `Assets/Gridline-Project-Import-Template.xlsx` as an `.xlsx` download (no auth required — `AllowAnonymous()`).
- [ ] The drop zone accepts drag-and-drop (`onDrop`) or a file `<input type="file" accept=".xlsx">` ("Choose file"); selecting/dropping a file calls `upload(file)`.
- [ ] `upload()` builds a `FormData` with the file under key `file` and calls `POST /api/imports/check` (multipart, no JSON `Content-Type` — the client only sets `Content-Type: application/json` when the body is not `FormData`). While the request is in flight, `busy` is true and the drop zone shows "Checking…".
- [ ] On success, the response (`Check` type: `token, ok, fileName, counts, issues[], project, trades[], partners`) replaces the drop zone with a review screen: file name, project name, and a "·"-joined summary of sheet counts (e.g. "12 trades · 4 zones"); a validation issues table (sheet, row, column, severity tag red=`error`/yellow=`warning`, message) shown only if `issues.length > 0`; a trades table (CSI code, title, budget formatted with `money()`, bidder count, a tag "New" (orange) or "Update" (green) per `t.match`); and a line reporting `partners.matched` existing trade-partner matches vs `partners.created` new ones that will be added.
- [ ] "Upload another file" resets `check` to `null`, returning to the drop zone (the previously uploaded batch/file on the server is left as-is; a new upload creates a new `ImportBatch`/token).
- [ ] On upload failure (e.g. non-.xlsx, missing Trades sheet, server error), the error message is shown in a `role="alert"` paragraph and the drop zone remains so the user can retry.
- [ ] The "Create project" footer button is disabled while `busy`, and in import mode is disabled until `check.ok` is true (i.e. `m.ErrorCount === 0` server-side) — a workbook with only warnings can proceed, one with any `error`-severity issue cannot.
- [ ] Only users with the `import.run` capability can check a workbook; without it the request is rejected (handled generically by the app's auth layer — see Architecture.md: Auth).

### Technical spec
**Frontend:** `web/src/pages/StartProject.tsx` (component `StartProject`, props `{ onClose, onCreated }`). State: `mode`, `check: Check | null`, `busy`, `err`, and the blank-form `form` (unused in this feature). Key handler: `upload(f?: File | null)`. API call: `api.post<Check>('/imports/check', fd)` where `fd` is a `FormData`. The `Check` type is declared locally in `StartProject.tsx` (not in `web/src/api/types.ts`): `{ token: string; ok: boolean; fileName: string; counts: Record<string, number>; issues: {sheet, row, column, severity: 'error'|'warning', message}[]; project: {name, number, client}; trades: {code, title, budget, bidders, match}[]; partners: {matched, created} }`. No SignalR involvement — nothing is committed to the shared project group yet (the batch isn't tied to a project/version).
**Backend:** `POST /api/imports/check` → `ImportEndpoints.Check(ctx, st, versionId: null)` in `api/src/Gridline.Api/Endpoints/ImportEndpoints.cs`. Requires capability `import.run` (`me.Require("import.run")`); no `Access.*` scope check runs for the new-project path since there is no project/version yet (`if (versionId is long vid) await Access.Version(w, vid)` is skipped when `versionId` is null). Also maps `GET /api/template.xlsx` (anonymous) and `POST /api/versions/{id}/imports/check` (the "trades into an existing version" variant, out of scope for this ticket). Logic: validates the upload is `.xlsx`, saves it via `Storage.Save` to `imports/{token}.xlsx`, parses it with `Template.Read(file, tradesOnly: false)` (`api/src/Gridline.Api/Import/Template.cs`) into an `ImportModel` (Project/Zones/Trades/Bidders/Crew/Requirements + `Issues`). Runs additional DB-backed checks only for new-project imports: project number uniqueness (`SELECT EXISTS ... FROM Project WHERE ProjectNo = @no`), state-code validity (`UsState`), and whether named Estimator/Project manager match an `AppUser` (warning only, not blocking). Cross-checks each trade's declared scope kit against active `ScopeKit` rows and flags unknown partner names as "will be added". Inserts one `ImportBatch` row (`Status = 'checked'` if `m.ErrorCount == 0` else `'failed'`) and up to 2000 `ImportIssue` rows, then returns the preview payload (`token, ok, fileName, bytes, ms, counts, issues (top 500, errors first), errors, warnings, project, trades (top 1000), partners`).
**Database:** Writes only `ImportBatch` (`PublicKey uuid UNIQUE` = the `token` the frontend holds, `FileName`, `Mode = 'newproject'`, `TargetVersionId NULL`, `Status IN ('uploaded','checked','created','failed','cancelled')`, `RowCounts jsonb`, `StartedBy → AppUser`) and `ImportIssue` (`BatchId → ImportBatch ON DELETE CASCADE`, `SheetName`, `RowNo`, `ColumnName`, `Severity CHECK IN ('error','warning')`, `Message`) — both defined in `db/migrations/001_init.sql`. Reads `Project`, `UsState`, `AppUser`, `ScopeKit`, `TradePartner` for validation only; nothing in those tables is modified. No triggers fire for this feature (neither table is in the `TrgTouch` list).

### Notes / edge cases
- `Template.Read` requires a "Trades" sheet to exist at all (error if missing) and additionally a "Project" sheet for the new-project path; both are hard blockers that make `ok=false` with no trades/project data returned.
- Re-uploading ("Upload another file") does not delete or cancel the previous `ImportBatch`/stored file — each check leaves its own row and its own `imports/{token}.xlsx` blob in storage; only the most recent `check.token` is held in frontend state and usable for create.
- The project-number-taken check only applies when the workbook specifies a project number; a blank project number is always allowed (auto-numbered on create, see ticket 02).
- Issues and trades are each capped (`Issues.Take(500)` / `m.Trades.Take(1000)`/`m.ErrorCount` based on the full, uncapped set) — a workbook with more rows than that will show a truncated preview even though the batch stores up to 2000 issues.
- "Estimator"/"Project manager" name matching is fuzzy (full name, email, or `first.last@`-style local part) and only warns, never blocks — the fields are simply left empty on create if unmatched.
