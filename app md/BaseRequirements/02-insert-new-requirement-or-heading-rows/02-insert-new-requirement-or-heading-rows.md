## Title
Base requirements — Insert new requirement or section-heading rows

### Summary
Lets an editor add new checklist rows: a single blank requirement at the end of the list ("Add requirement" button), a blank row or section heading right after a given row (right-click "Insert row below" / "Insert section heading below"), or a batch of 1–50 blank rows at once ("Insert rows below…"). Every inserted requirement row is immediately propagated onto every active trade in the version so it shows up in Scope match right away.

### User story
As an estimator building out the base requirements checklist, I want to insert new requirement lines or section headings anywhere in the list — one at a time or in bulk — so that I can structure the checklist to match how the project needs to be scoped, without retyping it per trade.

### Acceptance criteria
- [ ] "Add requirement" (toolbar button, only visible when editable) appends one new row with placeholder text "New requirement" after the current last line, with `desired = 'included'`, and shows a success toast "Row added to every trade".
- [ ] Right-click a row → "Insert row below" adds one blank requirement row immediately after that row (same section as the row it was inserted after) with a success toast "Row added to every trade"; this menu item has no explicit success message override beyond the default behavior described for `add`.
- [ ] Right-click a row → "Insert section heading below" adds one heading row ("New section" text) immediately after that row, with `isHeading = true` and no `desired` value.
- [ ] Right-click a row → "Insert rows below…" opens a modal asking "How many rows? (1–50)" (default 10, numeric input); submitting clamps the value to the 1–50 range (rounding non-integer input) and inserts that many blank requirement rows in one batch, with a toast "{n} rows added".
- [ ] Context-menu insert actions are only available when editable (right-click is a no-op — the menu never opens — when `canEdit` is false).
- [ ] New rows inherit the `sectionName` of the row they were inserted after (or default to "General" when inserted at the very end with no following context, or there is no prior row).
- [ ] Every inserted requirement row (not heading-only inserts are excluded — headings get their own `ScopeLine` row too) is written onto every active (non-archived) trade of the version so it immediately appears in that trade's Scope match grid with the same text/section/heading/desired values and an empty answer.
- [ ] If the version's checklist is still the shared company template (first edit on this version), the insert transparently copies the template into a new version-owned checklist first (copy-on-write) — the user sees no extra step, but every other version/project referencing the original template is unaffected.
- [ ] Locked-version / viewer behavior: insertion is blocked entirely at the UI (actions hidden) when `project.access === 'viewer'` or `version.status === 'locked'`; if attempted anyway the backend returns 403 (insufficient access) or 423 (locked version).

### Technical spec
**Frontend:** `web/src/pages/project/BaseRequirements.tsx`. The `add(after, body, ok)` helper calls `api.post<ReqData>(\`/versions/${vid}/requirements/lines\`, { afterId: after?.requirementLineId ?? null, sectionName: after?.sectionName, ...body })` and writes the response straight into the query cache (`qc.setQueryData(key, d)`) plus invalidates every cached query whose key starts with `'scope'` (so Scope match refetches). The toolbar "Add requirement" button calls `add(lines[lines.length - 1] ?? null, { lineText: 'New requirement' }, 'Row added to every trade')`. The context menu (`menu()` handler, built in `ContextMenu`) wires: "Insert row below" → `add(l, { lineText: '' }, 'Row added to every trade')`; "Insert section heading below" → `add(l, { isHeading: true, lineText: 'New section' })`; "Insert rows below…" → opens `<AskText>` which, on save, computes `n = clamp(round(+v || 1), 1, 50)` and calls `add(ask.after, { count: n, lineText: '' }, \`${n} rows added\`)`.
**Backend:** `POST /api/versions/{id}/requirements/lines` in `Endpoints/ScopeExtrasEndpoints.cs`, body `ReqLineIn(long? AfterId, string? SectionName, string? LineText, string? Desired, bool? IsHeading, int? Count)`. Calls `Access.Version(w, id)` (default `need = "editor"` — throws 403 below editor rank, 423 if the version is locked) then `OwnSet(w, id)` (copy-on-write, see Notes). Clamps `Count` to 1–50. Computes a fractional `SortKey` between the anchor row (`AfterId`, or the current max if none) and the next row after it; if the gap is too small to subdivide (`(hi-lo)/(n+1) < 0.0005`) it first calls `Renumber(w, set)` (spaces every line's `SortKey` to multiples of 10) and recomputes. For each of the `n` new rows it inserts one `RequirementLine` (`SectionName` defaults from the anchor row's section or `"General"`; `LineText` defaults to `"New section"`/`"New requirement"` depending on `IsHeading`; `Desired` defaults to `'included'` for non-headings, `NULL` for headings) and one `ScopeLine` per active trade (`Section = 'baserequirement'`) copying the new line's text/section/heading/desired. After the loop it re-syncs every affected trade's `ScopeLine.SortKey` to match the parent `RequirementLine.SortKey`. Logs `w.Log(projectId, id, "requirement.create", "version", id, after: new { count = n })` then commits (which also broadcasts the SignalR `changed` event). Returns the full `Requirements(...)` payload (same shape as the GET).
**Database:** Writes `RequirementLine (RequirementSetId, SortKey, SectionName, IsHeading, LineText, Desired)` and, per active trade, `ScopeLine (TradeId, Section, RequirementLineId, SortKey, IsHeading, LineText, Desired, ChangedBy)` — `Section` is the `LineSection` enum value `'baserequirement'`. The `ScopeLine` insert selects from `Trade WHERE VersionId = @id AND ArchivedAt IS NULL`. Index `IxRequirementLineSet (RequirementSetId, SortKey)` backs the sort-key gap queries; `IxScopeLineTrade (TradeId, Section, SortKey) WHERE ArchivedAt IS NULL` backs the trade-sync update. `ScopeLine` has `TrgTouch` attached (refreshes `ChangedAt` on UPDATE, not on this INSERT path). `ActivityEvent` row logged via `Work.Log` drives the `changed` SignalR broadcast.

### Dependencies
- Depends on ticket 01 (view) for the grid the new rows appear in, and shares the `OwnSet` copy-on-write mechanism with tickets 03 (edit), 05 (delete) and 06 (apply template).
- Downstream: Scope match (`app md/ScopeMatch`) must refetch its `scope`-keyed queries to show the new line on every trade — driven by the client-side `qc.invalidateQueries({ predicate: q => q.queryKey[0] === 'scope' })` call, not a server push.
- See `_Overview/Architecture.md`: Authorization/scoping (`Access.Version`, 423 locked), Unit of work (`Work.Begin`/`Work.Log`/`Work.Commit` and the `changed` broadcast), Database conventions (fractional `SortKey` pattern).

### Notes / edge cases
- **Copy-on-write (`OwnSet`)**: the first mutating call against a version whose `RequirementSetId` still points at a shared template (`IsTemplate = true`) — or that shares its set with more than one `ProjectVersion` — clones every `RequirementLine` row into a brand-new `RequirementSet` (named `"{Project} v{N} – base requirements"`, `IsTemplate = false`), remaps every existing `ScopeLine.RequirementLineId` on this version's trades to point at the cloned rows (preserving answers), and repoints `ProjectVersion.RequirementSetId` at the new set — all inside the same transaction as the insert. This means the very first insert/edit/delete on a version using a template is more expensive and touches rows across the whole version's trades, not just the one line being added.
- A version with a brand-new blank `RequirementSetId` (no set at all) — note `OwnSet` still handles this: `cur.set` is `null`/not a template, so it creates a fresh set directly.
- `Renumber` is a rare fallback (only triggered when fractional sort-key subdivision runs out of precision after many inserts between the same two rows); it rewrites every line's `SortKey` in the set, which also means every trade's synced `ScopeLine.SortKey` is rewritten in the same request via the trailing `UPDATE ScopeLine ... SortKey = r.SortKey` statement.
- Inserting a row does **not** call `Calc.Recalc` (unlike edit/delete) — a brand-new blank requirement line has no answer yet, so there's nothing to recalc.
