## Title
Scope match — Zone breakdown entries and remainder calculation

### Summary
A locked, special-purpose section of the scope grid where each bidder enters their price for each of the project's zones (breakout areas), with one zone designated as the "remainder" — automatically calculated as the bid's total minus the sum of the other zones — rather than typed. This lets the estimator see how each bid splits across buildings/floors/phases without the bidder needing to answer every scope line per zone.

### User story
As an estimator comparing bids across multiple buildings or phases, I want each bidder's price broken into zone amounts (with the last zone calculated automatically), so that I can see how their money is distributed without asking them to reconcile it themselves.

### Acceptance criteria
- [ ] The "Zones" section lists one `ScopeLine` per zone (`section = 'zone'`), each showing a colour swatch (`Zone.Colour`, default `#6a32d4`), the zone's name, and metadata (`floorArea`/`areaUnit`, `unitCount`/`unitLabel` unless the label is `N/A`) joined with `·`.
- [ ] Section description reads "Each bidder's amount per zone · names follow Project profile → Zones" and the section is locked: no insert/delete/indent/heading controls, no drag-reorder.
- [ ] Every zone cell except the remainder zone accepts only a dollar amount (or blank); clicking it opens `CellInput` with placeholder "Amount for this zone, e.g. 125000"; the remainder zone's cell is never clickable — clicking shows a toast "The remainder zone is calculated: bid total minus the other zones" and the cell instead displays the computed value, tagged "calculated" styling, with a title tooltip explaining it.
- [ ] The remainder amount shown is `round((bid.totalAmount − sum of the bidder's other zone amounts) × 100) / 100`; if the bid has no `totalAmount` yet, it shows "—".
- [ ] A summary row below the zone lines reads either "Zones total · matches the bid total" (when a remainder zone exists) showing each bid's total amount, or "Not in a zone · bid total minus the zones (pick a remainder zone in Project profile → Zones)" showing the un-zoned remainder per bid, flagged with a warning style when that leftover is non-zero.
- [ ] Right-clicking a zone cell offers: Edit note, "Clear amount" (only when it's not the remainder cell; clears the value), the 3 colour actions, and the locked "(Please edit zones in Project profile → Zones)" link.
- [ ] Zone answers participate in the same optimistic-save/rollback, rowRev-conflict, and realtime-focus behaviour as ticket 01's grid (same `saveCells`/`PUT /answers` path), but are always excluded from scope-adjustment totals and from the Trade-items search/gap-count/coverage calculations (`countable` explicitly filters out `section === 'zone'`).
- [ ] When `!canEdit`, zone cells render read-only amounts (no inline editor), same as other sections.

### Technical spec
**Frontend:** `web/src/pages/project/ScopeMatch.tsx` — the `zone` branch inside the `SECTIONS.map` row renderer (uses `zoneOf`, `zoneLines`, `remLine`, `zoneSum()`, `remainder()`, `zoneMeta()`); reuses `CellInput`/`saveCells`/`openMenu` from ticket 01 with `section === 'zone'` branches. `ScopeZone` fields come from `ScopeData.zones` (`GET /trades/{tradeId}/scope`); zone colour/area/unit metadata is read-only here (edited on Project profile).
**Backend:** Zones themselves are not created/edited from any Scope match endpoint — `ScopeEndpoints.Load` just joins `Zone` (`SELECT z.ZoneId, ZoneCode, ZoneName, FloorArea, AreaUnit, UnitCount, UnitLabel, IsRemainder, Colour FROM Zone z JOIN Trade t ON t.VersionId = z.VersionId WHERE t.TradeId = @tradeId ORDER BY z.SortOrder`). Zone-line answers are saved through the same `PUT /answers` (`ScopeEndpoints`) as ticket 01, with the zone-specific branch: looks up each line's `(section, isHeading, remainder)` via a `LEFT JOIN Zone z ON z.ZoneId = l.ZoneId`; rejects writes to the remainder line (`ApiException.Bad`); rejects any `Kind` other than `amount`/`blank` on non-remainder zone lines. A trade's **zone split percentages** (not the per-bid amounts shown here) are a separate concept maintained by `PUT /trades/{id:long}/zones` (`TradeEndpoints`), which explicitly refuses to run when `Trade.ZonesFromScope` is true ("This trade's zone split comes from the zone amounts in Scope match. Change them there…") — i.e. once a trade has per-bid zone answers, those answers (not a manual split) drive `TradeZone.Share`.
**Database:** `Zone` (`ZoneId` PK, `VersionId` FK→`ProjectVersion` cascade, `ZoneCode`/`ZoneName`, `SortOrder`, `FloorArea`, `AreaUnit CHECK IN ('SF','RSF','GSF','USF')`, `UnitCount`, `UnitLabel DEFAULT 'N/A' CHECK IN ('N/A','Unit','MW','Key','Space')`, `DefaultShare`, `Colour char(7)`, `IsRemainder boolean DEFAULT false`); unique partial index `UxZoneRemainder ON Zone (VersionId) WHERE IsRemainder` — **only one remainder zone per version** is allowed. `ScopeLine.ZoneId` FK→`Zone` ON DELETE CASCADE (deleting a zone deletes its `ScopeLine` rows on every trade, which cascades to `ScopeAnswer` via `ScopeLine`'s own ON DELETE CASCADE). `TradeZone` (`TradeId`, `ZoneId`, `Share numeric(7,4)`, composite PK) stores the trade-level split percentage referenced by `Trade.ZonesFromScope`/`ZoneShares` (Bid board/Price roll-up), distinct from the per-bid `ScopeAnswer.Amount` values shown on this tab.

### Dependencies
- Zones themselves (name, area, unit count/label, colour, which one is the remainder) are managed on **Project profile → Zones** — this ticket only consumes them; link in the row context menu navigates there (`../profile?tab=zones`).
- Feeds the Bid board / Price roll-up's zone split math (`Trade.ZonesFromScope`, `TradeZone.Share`) — see Architecture.md and the Bid board / Price roll-up page tickets for how `ZoneShares` is consumed downstream.
- Shares `saveCells`/`PUT /answers` and realtime focus/conflict behaviour with ticket `01-scope-item-answer-grid.md`.
- See `_Overview/Architecture.md`: Authorization/scoping, Unit of work, Recalculation engine, Database conventions (versioning model).

### Notes / edge cases
- A version can have zero zones (new projects often do); the Zones section then simply renders no rows, and the "Not in a zone" summary row still shows the full, un-split bid total per bidder.
- If a version has zones but none is marked `IsRemainder`, every zone line is directly editable (no calculated cell) and the "Not in a zone" leftover row becomes the de-facto remainder indicator — mismatches there are a strong signal the estimator forgot to total the bidder's zones correctly, since nothing stops `zoneSum(b) !== bid.totalAmount`.
- `remainder()` rounds to the cent using the same half-up convention noted in `Gridline.Calc.Rules` ("rounding matches JavaScript's Math.round... to cents") — replicate that rounding exactly or zone totals will visibly drift by a cent from the bid total.
- Changing which zone is `IsRemainder` on Project profile does not retroactively clear/move any `ScopeAnswer` amounts already entered on the old remainder zone's line — those answers remain stored (and become directly editable) until someone clears them.
- `ZonesFromScope` is a one-way gate: once true, `PUT /trades/{id}/zones` is a dead end for that trade until the zone answers are cleared (there's no endpoint here to flip it back off; that must happen elsewhere or not at all in the current code).
