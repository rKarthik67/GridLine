## Title
Scope match — Scope item row management (insert/delete/reorder/indent/headers, apply a scope kit)

### Summary
Lets the estimator shape the "Trade items" section of the scope grid itself — inserting blank rows or header rows at a chosen position, dragging rows to reorder them, indenting sub-items, converting a row to/from a header, flagging a row to be excluded from scope-adjustment math, deleting rows, and bulk-adding a trade's standard scope lines from a reusable "scope kit" template.
This is the row-structure counterpart to ticket 01 (which only edits the per-bid answer values).

### User story
As an estimator setting up a trade's scope, I want to add, reorder, indent and delete scope-item rows (and pull in a standard scope kit), so that the checklist matches how the trade is actually scoped before I start leveling bids.

### Acceptance criteria
- [ ] Right-clicking a "Trade items" row offers: Insert row / Insert 10 rows / Insert 50 rows / Insert header row (all insert **before** the clicked row), Change to normal row / Change to header row (disabled if already that type), Indent Right/Left (disabled past indent 5/at indent 0), Exclude/Include in Scope Adjustments (disabled if already that state or the row is a heading), 3 colour actions, Edit note, and Delete row (danger-styled).
- [ ] Right-clicking a "Base requirements" row instead offers only Edit note, colours, and a locked "(Please edit item in Base requirements)" link that navigates to `../base-requirements`.
- [ ] Right-clicking a "Zone" row instead offers Edit note, (Clear amount if not the remainder zone), colours, and a locked "(Please edit zones in Project profile → Zones)" link that navigates to `../profile?tab=zones`.
- [ ] When `!canEdit`, the context menu shows only a single disabled "Read only" item.
- [ ] The "Trade items" section header has an "Add rows" button prompting "How many blank rows? (1–50)" (default 10, clamped 1–50) and inserting them **after** the last trade-item row.
- [ ] The fx-bar toolbar has Indent left/right buttons (act on the selected row, disabled unless a trade-item row is selected) and Insert row / Header row buttons (insert before the selected row, or at the end if nothing is selected).
- [ ] Trade-item (non-heading) rows and header rows are draggable (`draggable={canEdit && sec === 'tradeitem'}`); dropping one onto another trade-item row moves the dragged row to just before the target (`moveBeforeLineId`), preserved by the dragged row's current `rowRev`.
- [ ] Line text is edited in place (`AutoText`): click-to-edit is not needed, it's always an inline textarea that grows with content; Enter (no Shift) blurs/commits, Escape reverts to the last saved value; saving an empty value falls back to a single space (`' '`) rather than truly empty text.
- [ ] The "Desired scope" select (Included/Excluded/Price/Text/–) is only editable on trade-item rows; choosing the blank option clears it (`clearDesired`); on other sections it renders as a read-only `Chip`.
- [ ] "Apply scope kit" (top toolbar, `canEdit` only) lists the company's scope kits (`lk.data.scopeKits`, each showing its name and line count) and, on choosing one, appends its lines to the end of the trade's items, skipping any line whose text (case-insensitive) already exists on the trade; shows a toast "{n} lines added from {kit name}".
- [ ] Deleting a row only works on `tradeitem` section lines (soft delete: `ArchivedAt`); the selection is cleared and the trade and bid-board caches are both invalidated/refetched.
- [ ] Every row-structure mutation (insert/patch/delete/apply-kit) that can change scope adjustments triggers a server recalculation and refreshes the Bid board cache (`vkey('bid-board', vid)`) in addition to the scope query.
- [ ] Attempting any row-structure edit while `!canEdit` is impossible from the UI (buttons/menus hidden or disabled); the server independently enforces this via `Access.Trade`/`Access.Line`'s editor-level check and the 423-locked-version rule.

### Technical spec
**Frontend:** `web/src/pages/project/ScopeMatch.tsx` — `openMenu()` (context menu builder), `insertLine()`, `lineSave()`, `dropOn()`, `AutoText` component, the "Apply scope kit" `Menu` in the page header, the fx-bar's indent/insert buttons, `editLineNote()`/`AskText` modal for line notes. Calls: `api.post<{lines: ScopeLine[]; firstLineId: number}>('/trades/{tradeId}/lines', { beforeLineId, afterLineId, count, isHeading, lineText })`; `api.patch('/lines/{lineId}', { lineText?, desired?, clearDesired?, isHeading?, indent?, skipInAdjustments?, lineNote?, moveBeforeLineId?, rowRev })`; `api.del('/lines/{lineId}')`; `api.post<{added: number}>('/trades/{tradeId}/apply-kit', { kitId })`. Lookups come from `useLookups()` (`lk.data.scopeKits`).
**Backend:** All in `ScopeEndpoints` (`Endpoints/ScopeEndpoints.cs`): `POST /trades/{id:long}/lines` — `scope.edit` capability + `Access.Trade` (editor+); rejects any `Section` other than `tradeitem`; clamps `Count` to 1–50; computes fractional `SortKey`s via `KeysFor` (placed strictly between the two neighbouring rows, renumbering the whole section to multiples of 10 if the gap is exhausted); inserts, logs `line.create`, commits, returns the new `ScopeLine`s. `PATCH /lines/{id:long}` — `Access.Line` (editor+), `CheckRev` against `ScopeLine.RowRev`; rejects text/heading/move edits on non-`tradeitem` sections (zone or base-requirement — different error messages); indent clamped 0–6; a move (`MoveAfterLineId`/`MoveBeforeLineId`) first pushes the row far out of order (`SortKey = -SortKey - 1000000`) then re-keys it via `KeysFor`; triggers `Recalc.TradeAndSummary` only when `SkipInAdjustments` or `IsHeading` changed; logs `line.update`. `DELETE /lines/{id:long}` — only allowed for `tradeitem` section; soft-deletes (`ArchivedAt = now()`); recalculates; logs `line.delete`. `POST /trades/{id:long}/apply-kit` — `Access.Trade`; `ApplyKit()` inserts `ScopeKitLine`s whose text isn't already present (case-insensitive) at the end of `tradeitem`, sets `Trade.KitId`, logs `trade.kit`.
**Database:** `ScopeLine` (`LineId` PK, `TradeId` FK→`Trade` cascade, `Section` enum `LineSection` (`baserequirement`/`tradeitem`/`zone`), `RequirementLineId` FK→`RequirementLine`, `ZoneId` FK→`Zone` cascade, `SortKey numeric(12,4)` fractional — "inserting never renumbers", `IsHeading`, `LineText`, `Desired` enum `DesiredKind`, `SkipInAdjustments`, `Indent smallint CHECK (0–6)`, `LineNote`, `ArchivedAt`, `ChangedAt`, `ChangedBy`, `RowRev int DEFAULT 1`); index `IxScopeLineTrade (TradeId, Section, SortKey) WHERE ArchivedAt IS NULL`. `ScopeKit`/`ScopeKitLine` (template source for "Apply scope kit"; `ScopeKitLine.SortKey`, `IsHeading`, `LineText`, `Desired`). Trigger `TrgTouch` on `ScopeLine` bumps `RowRev`/`ChangedAt` on every `UPDATE` (drives the `CheckRev`/optimistic-concurrency check in `PATCH /lines/{id}`).

### Dependencies
- Shares the grid and `ScopeData` payload with ticket `01-scope-item-answer-grid.md` (same `useQuery` key `['scope', vid, tradeId]`); row inserts/deletes change the set of cells ticket 01 can answer.
- "(Please edit item in Base requirements)" links to the Base requirements page (`pageKey=base-requirements`), which owns `RequirementLine`/`RequirementSet` edits that get pushed down onto every trade's `ScopeLine` copy.
- "(Please edit zones in Project profile → Zones)" links to Project profile's Zones tab, which owns `Zone` rows; see ticket `03-zone-breakdown-entries.md` for how zone `ScopeLine`s are generated/consumed.
- New trades created from the Bid board (`POST /versions/{id}/trades`) seed their starting `ScopeLine`s via `ScopeSetup.AddStandardLines` and `ScopeSetup.DefaultZoneSplit`, not this endpoint.
- See `_Overview/Architecture.md`: Authorization/scoping, Unit of work, Recalculation engine.

### Notes / edge cases
- `KeysFor`'s fractional sort-key scheme means two inserts at the "same" spot in quick succession from different tabs can legitimately interleave; if the gap between neighbours shrinks below `0.0005`, the whole `tradeitem` section is renumbered to multiples of 10 before retrying (one retry attempt only, then a 500).
- Moving a row via drag-and-drop temporarily sets a deeply negative `SortKey` (`-SortKey - 1000000`) mid-transaction before re-keying — a crash between those two statements would leave the row with a corrupt sort key (it's one transaction via `Work`, so this is actually atomic, but it is a non-obvious two-step update to replicate correctly).
- Base-requirement `ScopeLine`s are **copies** pushed from `RequirementLine` (see `ScopeExtrasEndpoints` on the Base requirements page) — editing them here is deliberately blocked; only `LineNote` and cell colour (ticket 01) are free-form per trade.
- "Change to header row" / "Change to normal row" and "Exclude/Include in Scope Adjustments" are the only `PATCH /lines` calls that force a trade recalculation — plain text/indent/note edits do not, so a text-only edit will not show an updated totals hash.
- Deleting the only line referencing a `ZoneId` does not delete the `Zone` itself — zones are version-level and independent of any one trade's lines (see ticket 03).
