## Title
Scope match — Bid inbox: proposal reader (AI/rules-based PDF suggestions)

### Summary
The "Proposal reader" half of the Bid inbox tab: the estimator uploads a subcontractor's proposal PDF against a specific bid lane, a background worker reads it (OCR/keyword extraction, optionally an AI model) and proposes a base amount plus per-line answers with quoted evidence, and the estimator reviews each suggestion before any of it is applied to the lane's answers.

### User story
As an estimator, I want to upload a sub's proposal PDF and get suggested scope answers with the exact quoted text they came from, so that I can fill in a bid lane quickly without re-typing a long written proposal by hand, while still deciding line-by-line what to trust.

### Acceptance criteria
- [ ] "Proposal reader" shows a bidder picker (every bid on the trade) and an "Upload proposal PDF" button (`canEdit` only); the button reads "Uploading…" while busy.
- [ ] Only a `.pdf` file is accepted; uploading starts a toast "Proposal uploaded · reading it now" and adds the reading to the list immediately (status `queued`).
- [ ] The readings list shows, per reading: the bidder's name, either "read {date}" (finished) or "in the queue", and a status tag (green "{n} to review" when done with pending suggestions, red for failed, yellow otherwise); "Open" is disabled while `queued`/`running`.
- [ ] While any reading for this trade is `queued` or `running`, the scope query polls every 2 seconds (invalidate-and-refetch) so the status flips to `done`/`failed` without a manual refresh.
- [ ] Opening a reading shows: the model name used (bottom-left of the footer), an error banner if `errorText` is set, a plain-language summary if present, a checkbox to apply a found base amount (pre-checked when one was found) labelled "Use base bid {found} (now {current})", and a table of suggestions: the matched scope line text (or a yellow "No matching line" tag when the suggestion couldn't be matched to any line), the suggested answer as a `Chip` (with a note if it differs from the line's current answer), the quoted evidence text and page number, a confidence percentage, and a per-row Accept/Reject segmented control.
- [ ] Suggestions default to `Accept` if they matched a line, `Reject` if they didn't (`decision === 'pending'` is mapped to `accepted`/`rejected` client-side based on whether `lineId` is set) — this is a **UI default only**; nothing is written until "Apply" is pressed.
- [ ] "Reject all" / "Accept all" buttons bulk-set every row's choice without saving.
- [ ] "Apply" (disabled while busy or while the reading isn't `done`) posts every suggestion's chosen decision plus the base-amount checkbox state in one call, shows "Decisions saved", and closes the modal back to the inbox (which refreshes the trade/scope caches).
- [ ] Accepted suggestions that matched a line become that bid's `ScopeAnswer` for that line (kind/amount/text copied from the suggestion, source tagged `proposal`), replacing whatever was there; accepted suggestions with no matching line are simply marked decided and never produce an answer.
- [ ] If the "use base bid" checkbox was checked and a base amount was found, the bid's base amount/state/`isPosted` are updated the same way a manually-entered base bid would be, sourced as `proposal`.
- [ ] The trade is recalculated and totals refreshed after Apply.

### Technical spec
**Frontend:** `web/src/pages/project/ScopeMatch.tsx` — `InboxTab` (proposal-reader column), `ReadingModal`, `Suggestion` interface. Data: `data.readings` is part of `ScopeData` (same `GET /trades/{tradeId}/scope` as ticket 10); the polling query `useQuery(['scope-poll', vid, tradeId], ...)` re-invalidates `['scope', vid, tradeId]` every 2s while any reading is `queued`/`running` (`refetchInterval`). `ReadingModal` fetches `useQuery(['reading', id], () => api.get<{reading, suggestions: Suggestion[]}>('/readings/{id}'))`. Upload: `FormData` with the PDF under `file`, `api.post<{readingId: number}>('/bids/{bidId}/proposals', fd)`. Apply: `api.post('/readings/{id}/decide', { items: [{suggestionId, decision}], applyBase })`.
**Backend:** All in `Endpoints/DocumentEndpoints.cs` plus the worker in `Proposal/ProposalReader.cs`. `POST /bids/{id:long}/proposals` (`.DisableAntiforgery()`) — requires capability `proposal.read`; `Access.Bid` (editor+); validates the upload is a `.pdf` under 50 MB; stores it under `proposals/{projectId}` via `Storage.Save`, inserts a `Document` row (`DocKind = 'proposal'`); inserts a `ProposalReading` row (`Status = 'queued'`); logs `proposal.upload`; commits, then enqueues the reading on the in-process `ProposalQueue` background worker (`queue.Add(rid)`) and returns `202 Accepted`. `GET /readings/{id:long}` — resolves the reading's bid then `Access.Bid` (viewer+); returns the reading plus its suggestions, each left-joined to the matched `ScopeLine` (for display text/section/desired) and to the **bid's existing** `ScopeAnswer` on that line (`currentKind`/`currentAmount`, so the modal can show "(now X)"), ordered unmatched-last then by scope order. `POST /readings/{id:long}/decide` — requires capability `scope.edit`; loads the reading (bid id, found base amount, status), 404 if missing, 400 if not yet `done`; `Access.Bid` (editor+); applies `All` (bulk accept/reject every still-pending suggestion) then any individual `Items` decisions; **only then** inserts/updates `ScopeAnswer` from every `accepted` suggestion that has a `LineId` (one row per distinct line, latest decision wins via `DISTINCT ON (s.LineId) ... ORDER BY s.LineId, s.DecidedAt DESC`), source `proposal`; optionally updates the `Bid`'s base amount/state/`IsPosted` when `ApplyBase` and a found amount exist; recalculates the trade; logs `proposal.decide`.
**Background job:** `Proposal/ProposalReader.cs` — a queue-driven worker (see Architecture.md: Background services) that picks up a `ProposalReading`, reads the uploaded PDF with PdfPig, optionally calls Azure OpenAI if configured, else falls back to a rules-based base-amount/keyword reader, and writes the reading's `Status`/`ModelName`/`BaseAmountFound`/`Summary`/`ErrorText`/`FinishedAt` plus one `ProposalSuggestion` row per proposed answer (with `Evidence`, `PageNo`, `Confidence`).
**Database:** `ProposalReading` (`ReadingId` PK, `BidId` FK→`Bid` cascade, `DocumentId` FK→`Document` cascade, `Status` enum `JobStatus` (`queued`/`running`/`done`/`failed`), `ModelName`, `BaseAmountFound`, `Summary`, `ErrorText`, `StartedAt`/`FinishedAt`, `StartedBy`). `ProposalSuggestion` (`SuggestionId` PK, `ReadingId` FK→`ProposalReading` cascade, `LineId` FK→`ScopeLine` ON DELETE CASCADE **nullable** — null means an unmatched exclusion/item, `Kind` enum `AnswerKind`, `Amount`, `AnswerText`, `Evidence`, `PageNo`, `Confidence numeric(4,3)`, `Decision` enum `ReviewDecision DEFAULT 'pending'`, `DecidedBy`, `DecidedAt`). Applying writes to `ScopeAnswer` and `Bid` exactly as described in ticket 01/04's schema notes.

### Dependencies
- Shares the `Document` table/upload constraints with ticket `08-trade-files-tab.md`, but only this upload path (`POST /bids/{id}/proposals`) creates a `ProposalReading` and enqueues the background worker — uploading the same file via the Files tab does not.
- Writes `ScopeAnswer`/`Bid.BaseAmount` consumed by tickets 01 and 04; the same "accept a suggested answer onto a line" concept as ticket 10's submission review, but sourced from AI/rules extraction instead of the subcontractor's own portal entry (`Source` is `proposal` vs `portal`).
- Depends on the `ProposalReader` background worker and `ProposalQueue` described in `_Overview/Architecture.md`: Background services.
- See `_Overview/Architecture.md`: Authorization/scoping, Unit of work, Recalculation engine, Background services (`ProposalReader`), Import/Export-adjacent storage handling.

### Notes / edge cases
- The 2-second poll (`refetchInterval: running ? 2000 : false`) runs for as long as **any** reading on the trade is queued/running — uploading a second proposal while the first is still being read keeps polling going rather than starting a second independent poll loop.
- `Confidence` and `Evidence` are whatever the worker produced — when Azure OpenAI isn't configured, the rules-based fallback reader is used instead (see Architecture.md), and its confidence/evidence quality will differ meaningfully from the AI path; don't assume a uniform confidence scale across environments.
- Applying decisions is **idempotent per suggestion row** but not globally transactional with the upload — a reading stuck in `running` (worker crash) has no exposed retry/cancel action on this tab; "Open" stays disabled and the poll loop runs indefinitely until the status changes server-side.
- A suggestion with no `LineId` can still be "Accepted" in the UI, but accepting it has no effect on `ScopeAnswer` (the decide endpoint's INSERT is filtered `WHERE s.LineId IS NOT NULL`) — it's just marked `accepted` for bookkeeping, which can confuse an estimator who expects "Accept" to always do something visible.
- Re-uploading a new proposal for the same bid does not remove or supersede a previous reading's suggestions — old readings (and their suggestion decisions) remain in the list indefinitely, so the "{n} to review" badge is per-reading, not per-bid.
