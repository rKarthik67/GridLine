## Title
Scope match — Qualifications tab (assumptions, exclusions, qualifications)

### Summary
Lets the estimator maintain free-text qualification statements for a trade — assumptions, exclusions, or general qualifications — either scoped to just this trade or marked "whole project" so they show on every trade, each flaggable as client-visible or internal-only, with reusable qualification sets to bulk-add boilerplate language.

### User story
As an estimator, I want to record assumptions, exclusions and qualifications per trade (or project-wide) and mark which ones the client should see, so that the scope comparison carries the caveats that go with each bid.

### Acceptance criteria
- [ ] The tab shows two lists: "This trade" and "Whole project" (labeled "shown on every trade"); each row has a Kind dropdown (Assumption/Exclusion/Qualification), an inline-editable text cell, a "Client sees it" checkbox, and (when editable) move-up, "make project-wide"/"make trade only" toggle, and delete buttons.
- [ ] Each list shows "None yet." when empty.
- [ ] Three "+ {Kind}" buttons under "This trade" each add one new trade-scoped qualification pre-filled with "New {kind}" text; one "+ Project qualification" button under "Whole project" adds one new project-wide qualification (`kind: 'qualification'`, pre-filled "New project qualification").
- [ ] "Add from set" (This-trade section only) lists reusable qualification sets (name + line count) and, on choosing one, appends every line from that set whose text doesn't already match (case-insensitive) an existing trade-scoped qualification; toast "Qualifications added".
- [ ] Saving a blank qualification text is a no-op (the server keeps the previous text when the trimmed input is empty) — it does not clear the row to blank.
- [ ] "Make project-wide" / "Make trade only" moves the row between the two lists by nulling/setting its `TradeId`; this happens without deleting/recreating the row (its id, kind, text and client-visibility are preserved).
- [ ] The move-up button is hidden on the first row of a list; it swaps sort order with the row directly above (not a full reorder) by picking a sort key between that row and the one before it.
- [ ] Deleting a row removes it permanently (no confirmation dialog, no archive/undo) and both lists refresh from the server's response.
- [ ] All editing controls (kind select, text, checkbox, move/toggle/delete buttons, both add-row buttons, "Add from set") are hidden or disabled when `!canEdit`.

### Technical spec
**Frontend:** `web/src/pages/project/ScopeMatch.tsx` — `QualsTab({ tradeId, vid, canEdit })`, local `Qual` interface, `KINDS` constant. Data: `useQuery(['quals', vid, tradeId], () => api.get<{trade: Qual[]; project: Qual[]}>('/trades/{tradeId}/qualifications'))`; `useQuery(['qualification-sets'], () => api.get<{setId, setName, lines}[]>('/qualification-sets'))`. Mutations (each returns the full `{trade, project}` payload which replaces the cached query data via `put()`): `api.patch('/qualifications/{id}?tradeId={tradeId}', { kind? | qualText? | showToClient? | moveAfterId? | projectWide? })`; `api.del('/qualifications/{id}?tradeId={tradeId}')`; `api.post('/trades/{tradeId}/qualifications', { kind, qualText })` (or `{ kind: 'qualification', qualText, projectWide: true }` for the project-wide add button); `api.post('/trades/{tradeId}/qualifications/apply-set', { setId })`.
**Backend:** All in `Endpoints/ScopeExtrasEndpoints.cs`. `GET /qualification-sets` — no explicit access check beyond the global auth middleware; lists active `QualificationSet`s with their line counts. `GET /trades/{id:long}/qualifications` — `Access.Trade` (viewer+); `Quals()` helper runs the same `Qualification` query twice, once filtered `TradeId = @tradeId` ("trade" list) and once `TradeId IS NULL` ("project" list), both scoped by the trade's `VersionId`. `POST /trades/{id:long}/qualifications` — `Access.Trade` (editor+); `Kind` must be `assumption`/`exclusion`/`qualification`; `TradeId` is `null` when `ProjectWide == true`, else the trade id; `SortKey` = `max(SortKey) for that (VersionId, TradeId) group + 1`; logs `qualification.create`. `PATCH /qualifications/{id:long}?tradeId=` — resolves the qualification's own `VersionId` first (404 if missing) then `Access.Version` (editor+, not `Access.Trade` — see Notes); `Kind` validated if present; `MoveAfterId` (0 = move to top) computes a sort key between the target and its current next sibling within the same `(VersionId, TradeId)` group; `ProjectWide: true/false/null` sets `TradeId` to `NULL`/the query-string `tradeId`/unchanged respectively; logs `qualification.update`. `DELETE /qualifications/{id:long}?tradeId=` — same `VersionId` resolution + `Access.Version` (editor+); hard-deletes; logs `qualification.delete`. `POST /trades/{id:long}/qualifications/apply-set` — `Access.Trade` (editor+); inserts `QualificationSetLine` rows as trade-scoped `Qualification`s, skipping any whose text (case-insensitive) already exists on that trade; logs `qualification.set`.
**Database:** `Qualification` (`QualificationId` PK, `VersionId` FK→`ProjectVersion` cascade, `TradeId` FK→`Trade` cascade **nullable** — null means project-wide, `Kind text CHECK IN ('assumption','exclusion','qualification')`, `SortKey numeric(12,4)`, `QualText`, `ShowToClient boolean DEFAULT true`, `ChangedAt`, `ChangedBy`); index `IxQualificationTrade (VersionId, TradeId, SortKey)`. `QualificationSet` (`QualificationSetId` PK, `SetName UNIQUE`, `CodeId` FK→`WorkCode`, `IsActive`). `QualificationSetLine` (`QualificationSetLineId` PK, `QualificationSetId` FK cascade, `Kind` same check, `SortOrder smallint`, `QualText`). No `TrgTouch` trigger on `Qualification` — `ChangedAt`/`ChangedBy` are set manually in the `UPDATE` statement, and there is no `RowRev` column at all on this table.

### Dependencies
- Project-wide qualifications (`TradeId IS NULL`) are visible from every trade's Qualifications tab within the same version — editing one here affects what every other trade on the version sees.
- `ShowToClient` presumably drives a client-facing export/presentation elsewhere in the app (e.g. a proposal or Price roll-up client view) — verify against that consuming page before assuming this flag is purely cosmetic here.
- See `_Overview/Architecture.md`: Authorization/scoping (note the `Access.Version` vs `Access.Trade` inconsistency called out below), Unit of work.

### Notes / edge cases
- `PATCH`/`DELETE /qualifications/{id}` resolve access via `Access.Version`, not `Access.Trade`, even though the URL also carries a `tradeId` query parameter purely to shape the response — this means the edit/delete check is at the **version** level (any editor on the version can edit/delete any trade's or the project's qualifications), not scoped down to "only editors of that specific trade," which is a meaningfully looser check than most of this page's other mutations (`Access.Trade`/`Access.Line`/`Access.Bid`).
- There is no `RowRev`/optimistic-concurrency check on `Qualification` edits — concurrent edits from two tabs silently overwrite each other field-by-field (`coalesce(@X, X)` pattern), not wholesale, but still without conflict detection.
- "Move up" only ever swaps with the immediately preceding row in the same `(VersionId, TradeId)` group — there's no drag-and-drop or arbitrary reposition, unlike the scope-item rows in ticket 02.
- Moving a qualification to "project-wide" keeps its original `SortKey`, which was computed within the trade's group — it does not get re-keyed to fit sensibly among the existing project-wide rows, so it may jump to an unexpected position in the "Whole project" list.
- `qualText` is trimmed server-side and empty becomes a no-op fallback to the previous value (`coalesce(nullif(trim(@QualText), ''), QualText)`) — there is no client-side guard preventing the user from thinking they cleared a qualification when in fact nothing changed.
- `ScopeExtrasEndpoints.cs` (the same file as this tab's endpoints) also maps `GET /features`, reading `Setting` rows where `SettingKey LIKE 'feature.%'` into a `{ [flagName]: bool }` dictionary. It is not called anywhere in `web/src` (confirmed by a repo-wide search) — no page, including this one, reads it yet. Treat it as an unused/future feature-flag lookup, not part of this tab's behaviour; don't assume any current UI gating is driven by it.
