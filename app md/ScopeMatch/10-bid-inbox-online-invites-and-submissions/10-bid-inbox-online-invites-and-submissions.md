## Title
Scope match — Bid inbox: online bid links and submission review

### Summary
The "Online bids" half of the Bid inbox tab: shows every bid-portal invite sent for the trade, its status, lets the estimator resend a link or withdraw it, and lets them review a pending online submission (base bid + answers) and accept it into the bid lane or reject it. (Sending a brand-new invite is initiated from the Bid board, not this tab — see Dependencies.)

### User story
As an estimator, I want to see which trade partners have an online bid link, resend or withdraw it, and review/accept or reject what they submitted, so that an online bid flows straight into the same lane I'm comparing on Scope match.

### Acceptance criteria
- [ ] "Online bids" lists every invite for the trade: company name, email, "sent {date}" and, if opened, "· opened {date}", and a status tag (`sent`/`opened`/`submitted`/`withdrawn`/other, colour-coded: green for submitted, blue for opened, red for withdrawn, neutral otherwise).
- [ ] An invite with a pending submission shows a "Review" button (`canEdit` only) that opens the submission modal.
- [ ] An invite that is not `withdrawn` and not `submitted` (`canEdit` only) shows a "…" menu with "New link (resend)" and "Withdraw".
- [ ] "New link (resend)" generates a new token for the invite, copies the full portal URL (`location.origin + link`) to the clipboard (falls back to a toast showing the raw URL if clipboard access fails), and shows "New link copied" on success.
- [ ] "Withdraw" sets the invite's status to `withdrawn` (toast "Link withdrawn") and removes its action buttons from view on refresh.
- [ ] No invites yet shows "No bid links sent for this trade yet."
- [ ] The submission review modal shows the base bid amount, the count of submitted answers, the submission date, any notes the sub entered, and an explanation: "Accepting sets the lane's base bid and fills its answers (marked as from the portal). Existing answers on those lines are replaced."
- [ ] Accepting a submission: sets the linked `Bid`'s base amount to the submitted amount, marks it posted/`State = 'posted'`, and **overwrites** that bid's `ScopeAnswer` for every line the sub answered (source tagged `portal`), replacing any existing answer on those specific lines; the trade is recalculated and the modal closes back to the inbox with the trade/caches refreshed.
- [ ] Rejecting a submission simply records the decision (`rejected`) without touching the `Bid` or any `ScopeAnswer`.
- [ ] Attempting to decide a submission that has already been decided is rejected with a 409 ("This submission was already {decision}.").
- [ ] Both Accept and Reject buttons are disabled while the request is in flight (`busy`).

### Technical spec
**Frontend:** `web/src/pages/project/ScopeMatch.tsx` — `InboxTab` (online-bids column only; see ticket 11 for the proposal-reader column of the same tab) and `SubmissionModal`. Data: `data.invites` comes pre-loaded as part of `ScopeData` (`GET /trades/{tradeId}/scope`, same query as tickets 01/03); `SubmissionModal` separately fetches `useQuery(['submission', id], () => api.get<{baseAmount, answers, notes, submittedAt, companyName}>('/submissions/{id}'))` (note: `answers` is a JSON **string** the modal `JSON.parse`s client-side). Mutations: `api.post<{link: string}>('/invites/{inviteId}/resend')`; `api.del('/invites/{inviteId}')`; `api.post('/submissions/{id}/decide', { decision })`. On any change, `InboxTab`'s `onChanged` callback re-invalidates the scope query and the Bid board query.
**Backend:** All in `Endpoints/PortalEndpoints.cs` except the invite list itself, which is embedded in `ScopeEndpoints.Load` (`invites` subquery joining `BidInvite`→`TradePartner`, with a correlated subquery for the latest pending `BidSubmission.SubmissionId`). `POST /invites/{id:long}/resend` — requires capability `invite.send`; resolves the invite's trade then `Access.Trade` (editor+); generates a new token (`Tokens.New()`), stores only its hash (`Tokens.Hash`), resets `Status = 'sent'`, bumps `SentAt`, extends `ExpiresAt` to at least 14 days out; logs `invite.resend`. `DELETE /invites/{id:long}` — `Access.Trade` (editor+); sets `Status = 'withdrawn'` (soft, no row deleted); logs `invite.withdraw`. `GET /submissions/{id:long}` — resolves the submission's trade via `BidSubmission`→`BidInvite`, `Access.Trade` (viewer+); returns the submission plus the company name. `POST /submissions/{id:long}/decide` — `Decision` must be `accepted`/`rejected`; locks the row (`FOR UPDATE OF s`); `Access.Trade` (editor+) from the resolved trade; rejects if already decided (409 "duplicate"); on accept, updates `Bid` (`BaseAmount`, `BaseSource = 'portal'`, `State = 'posted'`, `IsPosted = true`) and bulk-upserts `ScopeAnswer` from the submission's stored `Answers` jsonb array (one `INSERT ... ON CONFLICT (LineId, BidId) DO UPDATE` sourced from `jsonb_array_elements`, joined back to `ScopeLine` to make sure the line is still on that trade); recalculates the trade (`Recalc.TradeAndSummary`, reason `portal.decide`); logs `portal.{decision}`.
**Database:** `BidInvite` (`InviteId` PK, `PublicKey uuid UNIQUE`, `TradeId` FK→`Trade` cascade, `BidId` FK→`Bid` ON DELETE SET NULL, `PartnerId`/`PersonId`, `SentToEmail citext`, `TokenHash bytea UNIQUE` — the raw token is **never** stored, only its hash, `Status` enum `InviteStatus`, `Message`, `SentAt`/`OpenedAt`/`SubmittedAt`, `ExpiresAt`, `SentBy`). `BidSubmission` (`SubmissionId` PK, `InviteId` FK→`BidInvite` cascade, `BaseAmount`, `Answers jsonb DEFAULT '[]'` — shape `[{lineId, kind, amount, text}]`, `Notes`, `SubmittedAt`, `Decision` enum `ReviewDecision DEFAULT 'pending'`, `DecidedBy`, `DecidedAt`). No `TrgTouch`/`RowRev` on either table.

### Dependencies
- Creating a **new** invite (`POST /trades/{id:long}/invites`) is not exposed from this tab's UI — per the current `ScopeMatch.tsx`, invites are only resent/withdrawn/reviewed here; sending the first link for a bid happens elsewhere (the Bid board's invite flow) and this tab simply reflects/acts on invites that already exist.
- Accepting a submission writes `ScopeAnswer` rows consumed by ticket `01-scope-item-answer-grid.md` and updates `Bid.BaseAmount` consumed by tickets 01 and 04.
- The anonymous public-facing side of this flow (`GET/POST /portal/{token}`, what the subcontractor actually sees and submits) lives on the separate `/bid/:token` route (`pages/Portal.tsx`) — out of scope for this page's tickets but is the origin of every `BidSubmission` reviewed here.
- See `_Overview/Architecture.md`: Authorization/scoping, Unit of work, Recalculation engine, Realtime (the public portal submit broadcasts a `changed` SignalR event too, via `IHubContext<ProjectHub>` directly rather than through `Work`).

### Notes / edge cases
- The portal submit endpoint (`POST /portal/{token}`, anonymous) broadcasts its `changed` SignalR event manually via `IHubContext<ProjectHub>` rather than through the `Work.Commit()` path every other mutation on this page uses — it is the one place on this feature set that bypasses the standard unit-of-work broadcast helper, because there's no authenticated `CurrentUser`/tab id to exclude.
- `TokenHash` being the only persisted form of the invite token means a lost/never-copied link cannot be recovered — "resend" is the only way to get a usable link again, and it immediately invalidates the previous one (new hash replaces the old).
- Accepting a submission **replaces** existing answers only on the lines the sub actually answered — any answers already on other lines for that bid (e.g. entered manually before the sub submitted) are left untouched, so a review should not be assumed to be a full reset of the bid's answers.
- `BidInvite.ExpiresAt` is extended, never shortened, by resend (`greatest(ExpiresAt, now() + interval '14 days')`) — resending a link that already expires far in the future does not pull its expiry closer.
- There is no UI affordance here to re-decide a submission after it's been accepted or rejected (the 409 is purely a backend guard) — a mis-click "Accept" cannot be undone from this tab.
