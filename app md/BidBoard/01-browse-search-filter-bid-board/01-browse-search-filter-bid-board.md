## Title
Bid board — Browse, search, and filter the trade grid

### Summary
The bid board shows every trade in the version as a row, with every bidder's price side by side, plus a position block (budget, lowest, buyout) and zone split columns. A search box, quick filter pills, column-visibility toggles, and a budget-source selector let the estimator narrow the grid down to what they need to work on, and a summary bar and footer totals keep the big picture visible while they do it.

### User story
As an estimator reviewing a version's trades, I want to search, filter, and toggle which position columns are shown so that I can quickly find the trades that still need attention (unresolved, not lowest, single bid, or with a plug/note) without scrolling past everything else.

### Acceptance criteria
- [ ] Page loads `GET /versions/{versionId}/bid-board` and renders one row per trade, one column pair (Total/$‑per‑SF) per zone, and one tile column per bid lane (plus an "Invite" add tile when the caller can edit).
- [ ] The search box filters rows client-side (no refetch) by case-insensitive match against `csiCode`, `tradeName`, and the joined `bidderName` of every bid on the trade.
- [ ] The filter pills are mutually exclusive (`all`/`unres`/`notlow`/`single`/`plug`) and filter client-side:
  - `unres` — `carriedValue == null`.
  - `notlow` — a bid is picked and its `totalAmount` differs from `t.lowestValue`.
  - `single` — fewer than 2 posted bids.
  - `plug` — trade has a `plugAmount`, `clientNote`, or `teamNote`.
- [ ] The "Only unresolved" toggle applies the same `carriedValue == null` rule as the `unres` pill, independently of which pill is selected (both checks are OR'd into the row filter).
- [ ] The "Budget" toggle shows/hides the Budget and "Δ budget" columns (position group) and the mini-bar's Budget/Δ budget tiles; it is purely a client-side display toggle, no refetch.
- [ ] The "Anticipated buyouts" toggle shows/hides the Buyout % and Buyout savings columns (`t.buyoutPct`, `t.budgetValue - t.carriedValue` when both are present).
- [ ] The "Budget source" menu (only shown when the Budget toggle is on) lists "Trade budgets (as entered)" plus every `BudgetColumn` for the project; choosing one calls `PATCH /versions/{versionId}` with `{ baselineName }` (empty string for "Trade budgets"), then invalidates the bid-board query; a toast confirms "Budget source: {name}".
- [ ] Each row shows CSI code, trade name (a link to Scope match for that trade), `{posted}/{total}` bid count, and (for editors) a kebab menu with Rename, Zone split, Add bidder, Open in scope match, and Delete trade.
- [ ] The "Picked value" column shows the resolved value (`carriedValue`) or an "Unresolved" tag when null, the picked bidder's name (or "Plug value" / "No bid picked"), and — when a company benchmark exists for the CSI code — a `$/SF` figure, highlighted when more than 10% outside the historical low–high range for similar projects.
- [ ] Bid tiles show lane letter, bidder name, rank (when ≥2 posted bids), amount or current status, a "Picked"/"Lowest" badge, and (for posted bids beyond the lowest) a heat bar sized by percent over the lowest bid.
- [ ] The Indirect costs & roll-up section below the trades lists every non-"trades" line from the price roll-up (`GET /versions/{versionId}/price-roll-up`), tagging `custom` kind lines and noting that `cost` lines come "From Project overheads" (code `genreq`) or "From Precon services" otherwise.
- [ ] The footer mini-bar shows Budget, Δ budget, Trades total, Δ to lowest, Lowest, Contract total (from the roll-up's "Contract total" line), and $/SF (trades total ÷ `version.grossArea`), colour-coded (bad/good/warn) per the current sign of each delta.
- [ ] When `project.access === 'viewer'` or `version.status === 'locked'`, all edit affordances (Add trade, Import trades, row kebab menu, adjust button, Invite tiles) are hidden or disabled; see Architecture.md: Authorization/scoping for the 423-locked rule.

### Technical spec
**Frontend:** `web/src/pages/project/BidBoard.tsx`, default export `BidBoard`. Data: `useQuery({ queryKey: vkey('bid-board', vid), queryFn: () => api.get<BidBoardData>('/versions/${vid}/bid-board') })` plus a second query for `vkey('price-roll-up', vid)` → `GET /versions/{vid}/price-roll-up` (`RollUpData`). Local state: `q` (search), `filter` (`Filter` union), `showBudget`, `onlyUnres`, `buyout` toggles. Row filtering is a `useMemo` over `data.trades`. The budget-source `Menu` item calls `api.patch('/versions/${vid}', { baselineName })` then `qc.invalidateQueries({ queryKey: key })`. `canEdit = project.access !== 'viewer' && version.status !== 'locked'`. Row highlight for concurrent editors uses `useOthersFocus('trade')` (keyed by `tradeId`) and `focus('trade', String(tradeId), 'viewing')` on tile hover — see Architecture.md: Realtime (SignalR).
**Backend:** `GET /versions/{id:long}/bid-board` in `Endpoints/TradeEndpoints.cs` — opens a read connection, calls `Access.Version(c, ctx.Me(), id)` (viewer-level scope check), then returns `{ version, zones, trades, budgets, baselineName, totalsHash }` where `trades = await LoadTrades(c, null, id)`. `GET /versions/{id:long}/price-roll-up` in `SummaryEndpoints.cs` calls `Access.Version(w, id, "viewer")` then `SummaryEndpoints.Build(w, id)` (never commits — read-only). `PATCH /versions/{id:long}` in `ProjectEndpoints.cs` requires editor access (`Access.Version(w, id, "editor")`), updates `ProjectVersion.BaselineName`, and when a baseline name was sent, calls `Budgets.ApplyBaseline(w, id)` then `Recalc.Version(w, id, "version.update")`.
**Database:** `LoadTrades` reads `Trade` (all non-archived columns for the version, ordered by `SortOrder NULLS LAST, CsiCode, ScopeNo`), `Bid` joined to `Trade` and left-joined to `TradePartner` (for the `AddedByUser` "*" marker) and a correlated subquery to `PartnerPerson` for contact/email, `TradeZone` joined to `Zone` for `zoneShares`, and a cross-project benchmark query over `Trade`/`ProjectVersion`/`Project` (restricted to other projects of the same `ProjectType` and `Stage IN ('submitted','awarded','lost','bidding')`) for the `$/SF` range badge. The bid-board endpoint also reads `BudgetColumn`/`BudgetValue` (join on `ProjectId`) for the budget-source menu options. `PATCH /versions/{id}` writes `ProjectVersion.BaselineName`; `Budgets.ApplyBaseline` then updates every `Trade.BudgetValue` in the version from `BudgetValue.Amount` where `BudgetColumn.BudgetName = ProjectVersion.BaselineName`. Indexes used: `UxTradeCode (VersionId, CsiCode, ScopeNo) WHERE ArchivedAt IS NULL`, `IxTradeProject`, `IxBidPartner`.

### Dependencies
Feeds every other Bid board ticket (they all mutate rows this view renders). Reads price-roll-up data also shown on the Price roll-up page (see `PriceRollUp` tickets) and reacts to Project profile → Zones (zone columns) and budget columns created on the Project profile page. See Architecture.md: Recalculation engine, Realtime (SignalR), Authorization/scoping.

### Notes / edge cases
- The grid's maximum bid-column count (`maxB`) is derived client-side from the widest trade's bid list (plus one "Invite" slot for editors), so adding a bid to any trade can shift every row's column count.
- `carriedValue`, `lowestValue`, `budgetDelta`, `buyoutPct`, and `zonesFromScope`/zone shares are server-computed and stored on `Trade` by the recalculation engine (see Architecture.md: Recalculation engine); this view only reads them — it never derives them itself except for the instant client-side preview in the "pick a bid" feature.
- The benchmark badge is **not** scoped to the current project/version in `WHERE`; it is an aggregate across every other project sharing the CSI code, `ProjectType`, and bidding-stage, so it changes over time as other projects are entered — don't mistake it for a stored, version-specific value.
- Switching "Budget source" overwrites every trade's `BudgetValue` in the version wherever the chosen `BudgetColumn` has a matching `CsiCode`; trades with no match in that column keep their current budget (not cleared).
- The roll-up query (`price-roll-up`) runs inside a `Work` transaction that is **never committed** (explicitly read-only), so it does not log an `ActivityEvent` or broadcast a `changed` event.
- The `$/SF` benchmark badge is **not** sourced from the standalone `GET /benchmarks` endpoint or its backing `TradeBenchmark` table — it's a separate, live, uncached cross-project aggregate computed inline inside `LoadTrades` (see Technical spec) every time the bid board loads. `GET /benchmarks` (reads `TradeBenchmark` by `csi`/`type` query params) has no caller anywhere in the web app today — it's an orphaned endpoint, not part of this page's feature set.
- `GET/POST /projects/{id}/budgets` (create/list a project's named `BudgetColumn`s) is also unused by the web app: the Budget-source menu here only *selects* an existing `BudgetColumn` as the baseline (via `PATCH /versions/{id}` → `Budgets.ApplyBaseline`) and the bid-board response's `budgets` array is read inline by the `GET /versions/{id}/bid-board` query, not via `GET /projects/{id}/budgets`. There is no screen anywhere in the current web app that creates a new named budget column — do not assume this page (or any other) exposes that endpoint's create path.
- `PUT /trades/{id}/lanes` (lane reorder/hide) is called only from Scope match (`web/src/pages/project/ScopeMatch.tsx`, function `lanes`), not from this page — Bid board always renders bid lanes in `LaneNo` order with no reorder/hide affordance of its own. See ScopeMatch ticket 04 for that feature; the two pages share the same `Bid.LaneNo`/`HiddenInScope` columns, so a lane hidden in Scope match still shows here (Bid board ignores `HiddenInScope`).
- `GET /trades/{id}` has no caller in the web frontend at all (neither this page nor Scope match fetch a single trade this way); every page that needs one trade's data gets it embedded in a list response (`LoadTrades`) or a `TradeReply`.
