## Title
Bid board — Import trades and bidders from Excel

### Summary
"Import trades" lets the estimator upload a filled-in copy of the Gridline Excel template's Trades/Bidders sheets, see a dry-run check (row counts, validation issues, and which trades are new vs. updates) before anything is written, and then commit the import in one transaction — adding new CSI codes, updating existing trades' budgets, and adding new bidders with their bids.

### User story
As an estimator with an existing bid tab spreadsheet, I want to upload it and see what will change before committing, so that I can bulk-load trades and bidders without manually re-entering each one and without risking a bad import.

### Acceptance criteria
- [ ] "Import trades" is shown only to editors; it opens a modal explaining it uses the Trades and Bidders sheets of the Gridline template, that new CSI codes are added and existing trades get their budget and any new bidders, with a "Download template" link (`/api/template.xlsx`).
- [ ] Choosing a `.xlsx` file immediately uploads it for checking; a non-`.xlsx` file is rejected ("Only .xlsx workbooks can be imported. In Excel, use Save As → Excel Workbook.").
- [ ] The check step **writes nothing to live tables** — only an `ImportBatch`/`ImportIssue` audit record — and returns: file name, per-sheet counts, an ok/not-ok flag, a list of issues (sheet, row, severity, message), and a preview table of trades (CSI, title, budget, bidder count, "New" vs. "Update").
- [ ] Errors (`severity: 'error'`) block the Import button; warnings do not.
- [ ] After a successful check, "Upload another" discards the check and returns to the file picker; "Import" is disabled until the check is `ok`.
- [ ] Clicking Import commits the previously-checked workbook in one transaction and closes the modal on success, reporting (via the page's own invalidation) trades added/updated and bids added.
- [ ] Only the user who uploaded a workbook can commit it; anyone else gets a 403.
- [ ] A workbook can only be committed once — a second attempt returns 409 "This workbook was already imported."
- [ ] If the workbook still has unresolved errors (shouldn't happen if the check gate was respected, but re-verified server-side), commit fails with "The workbook has problems. Upload it again to see them."
- [ ] Both the check and the commit require capability `import.run`.

### Technical spec
**Frontend:** `web/src/pages/project/BidBoard.tsx`, component `ImportTradesModal` (`setImportOpen(true)`), local `Check` type mirrors the check response. File picked → builds a `FormData` with the file and calls `api.post<Check>('/versions/${versionId}/imports/check', fd)`. Commit calls `api.post<{ tradesAdded; tradesUpdated; bidsAdded }>('/imports/${check.token}/create')`. On done, the page invalidates every query whose key contains `"v{vid}"` (bid-board, price-roll-up, scope-match, etc. — the same broad predicate used by trade delete).
**Backend:** `Endpoints/ImportEndpoints.cs`. `POST /versions/{id:long}/imports/check` (and the project-less `POST /imports/check` used for whole-new-project imports, not used from this page): requires `import.run`, requires a version-scope editor check (`Access.Version(w, vid)`) when a `versionId` is given, reads the multipart file, saves it to storage under `imports/{token}.xlsx`, parses it (`Template.Read(..., tradesOnly: true)` for the into-version mode), runs DB-aware checks (existing trades on this version by CSI code, known scope kits, known trade-partner names), inserts an `ImportBatch` row (`Status = 'checked'` or `'failed'`) and one `ImportIssue` row per issue (capped at 2000), and returns the check payload described above.
`POST /imports/{token:guid}/create`: requires `import.run`, locks the `ImportBatch` row (`FOR UPDATE`), enforces the ownership/duplicate/status rules above, re-reads and re-parses the saved workbook, calls `ImportService.IntoVersion(w, versionId, model)` (for a trades-into-version import — a from-scratch project import instead calls `ImportService.CreateProject`), marks the batch `created` with the resolved target ids, logs `import.trades`, and returns counts plus elapsed milliseconds.
`ImportService.Trades` (shared helper used by `IntoVersion`): stages the parsed rows into temp tables (`imptrade`, `impbid`, `impsplit`, `impreq`) via Postgres `COPY ... BINARY` for speed, then a sequence of set-based `UPDATE`/`INSERT ... SELECT` statements against the real tables, then calls `Recalc.VersionBulk(w, versionId, "import.trades")` (the set-based equivalent of per-trade recalculation, used for bulk imports of up to thousands of trades).
**Database:** `ImportBatch` (migration 001): `PublicKey uuid UNIQUE` (the "token" the frontend polls/commits by), `FileName`, `Mode CHECK (Mode IN ('newproject','tradesintoversion'))`, `TargetProjectId`/`TargetVersionId`, `Status CHECK (... IN ('uploaded','checked','created','failed','cancelled'))`, `RowCounts jsonb`, `StartedBy`. `ImportIssue`: `BatchId`, `SheetName`, `RowNo`, `ColumnName`, `Severity CHECK (IN ('error','warning'))`, `Message`. The import-into-version write path touches: `Trade` (updates existing rows' `BudgetValue`/`TeamNote`/`BidDueOn` by CSI-code match at `ScopeNo = 1`; inserts new rows for unmatched CSI codes, resolving `CodeId` via `WorkCode`/`CodeGroup`/`CodeEdition`, `KitId` via `ScopeKit` name match, and `EstimatorId` via a fuzzy `AppUser` name/email match), `TradePartner` (inserts new companies, `ON CONFLICT ((lower(CompanyName))) DO NOTHING` against `UxPartnerName`), `PartnerPerson` (inserts new contacts, de-duplicated by partner + email/name), `Bid` (inserts one row per trade/bidder pair not already present, `BaseSource = 'import'`), and `TradeZone` (replaces/derives splits from an `impsplit` sheet or falls back to each `Zone.DefaultShare`). `Recalc.VersionBulk` rewrites `Bid.ScopeAdjustments`/`TotalAmount` and `Trade.LowestValue`/`CarriedValue`/`BudgetDelta`/`BuyoutPct` set-based across the whole version.

### Dependencies
The target version must already exist (this import adds to an existing version's trades — it does not create projects or versions from this page). Reuses the same trade/partner-matching concepts as "Add a bidder to a trade"/"Add a trade" but as bulk, set-based SQL rather than the per-row endpoints. Feeds every ticket that reads `Trade`/`Bid` (the whole bid board). See Architecture.md: Import/Export, Db.cs (300s command timeout — sized for large imports).

### Notes / edge cases
- The check step persists an `ImportBatch`/`ImportIssue` audit trail even though it writes nothing to `Trade`/`Bid` — a failed or abandoned check still leaves a permanent row (`Status = 'checked'` or `'failed'`), and the uploaded file itself stays in storage keyed by the check's token.
- Existing-trade matching for the "update" path is scoped to `ScopeNo = 1` only (`t.ScopeNo = 1 AND t.CsiCode = i.code`) — a trade that was split into multiple scope numbers for the same CSI code will not be matched/updated by an import; only a fresh `ScopeNo = 1` row for a new code gets created.
- Duplicate-bid prevention on import is the same `(TradeId, PartnerId)` uniqueness idea as the manual Add-bidder path, but implemented as a set-based `NOT EXISTS` rather than catching a single conflict — a bidder already on the trade (by matched partner name) is silently skipped, not reported as an issue.
- The commit endpoint is one-shot per token (`Status = 'created'` blocks a repeat) but the *check* endpoint can be called repeatedly for the same version with new uploads, each producing a brand-new token/`ImportBatch`; there's no limit on how many checked-but-never-committed batches accumulate.
- `Recalc.VersionBulk`'s set-based math is documented as "kept identical by the API test that compares both on the seed data" against the per-trade `Rules.Trade` — if a future change adjusts one calc path, the other must be updated in lockstep or imported trades will total differently than manually entered ones.
