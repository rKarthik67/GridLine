## Title
Project profile — Manage fee carve-outs and bid total options

### Summary
The Fee carve-outs tab (was: Fee exclusions) lets an editor choose which cost categories are excluded from the fee calculation base, set the quoted fee %, decide whether each project reserve's base also includes precon services, and toggle whether project overheads are excluded from the direct cost total. Every change recalculates the fee and contract total immediately, with the UI showing an optimistic preview before the server responds.

### User story
As a project estimator, I want to carve specific cost categories out of the fee base and control how reserves and the direct cost total are calculated so that the quoted fee and contract total match the deal's commercial terms.

### Acceptance criteria
- [ ] "Apply fee carve-outs?" is a Yes/No segmented control; choosing No keeps the individual carve-out ticks saved but makes them not apply (the fee/contract total behave as if nothing were carved out), and the carved-out-columns section is visually dimmed.
- [ ] "Quoted fee (%)" is an editable number field; on blur (or Enter), if the value changed and parses to a number, it is saved; if the fee markup is switched off on the Rates tab, a warning is shown under the field.
- [ ] Three live KPIs are shown: Fee base (fee amount ÷ fee rate, when a fee rate is set), Fee (current fee amount, with a delta vs. what the fee would be with no carve-outs applied, colored favorably when the carve-outs reduce the fee), and Contract total.
- [ ] "Left out of the fee base" section lists checkboxes for project overheads, precon services, reserves (project/design/escalation combined), P&P bond, and works cover/builders risk — each showing its current dollar amount; a note clarifies trades and in-fee indirect items are always in the fee base.
- [ ] "Reserve base" section lists the three reserves (project/design/escalation), each with a checkbox for "include precon services" in that reserve's base, and its current dollar amount.
- [ ] "Bid total options" section has a checkbox "Leave project overheads out of the direct cost total", with explanatory text that this changes what reserves are based on while project overheads still count in the subtotal.
- [ ] Toggling any checkbox or selecting Yes/No immediately shows the new state in the UI (optimistic `pending` merge) before the server confirms, then reconciles with the server's authoritative roll-up response.
- [ ] Submitting an unknown carve-out key is rejected server-side with "Fee carve-outs can only be: genreq, precon, reserves, bond, cover."; an unknown reserve key is rejected with "Unknown reserve."; a fee % outside 0–100 is rejected with "Fee must be between 0 and 100%."
- [ ] All controls are disabled when `project.access === 'viewer'` or the version's `status === 'locked'`.
- [ ] Any successful save invalidates the markups and bid-board caches for this version in addition to updating the price-roll-up cache directly from the response.

### Technical spec
**Frontend:** `web/src/pages/project/Profile.tsx`, component `FeeCarveOuts({ project, version })`. Loads `useQuery({ queryKey: vkey('price-roll-up', vid), queryFn: () => api.get<RollUpData>(\`/versions/${vid}/price-roll-up\`) })` — carve-out state (`CarveOuts`) comes from `ru.data.carveOuts`, merged with a local `pending` partial-state overlay for optimistic UI. Uses `calcSummary` from `@gridline/calc` to compute `noCarve`, a browser-side "what the fee would be with carve-outs cleared" preview using the same rules as the server, purely for the KPI delta — this is not sent to the server. Save handler `put(body, ok)`: sets `pending` immediately, then `api.put<RollUpData>(\`/versions/${vid}/fee-carve-outs\`, body)`; on success writes the response straight into the TanStack Query cache via `qc.setQueryData(vkey('price-roll-up', vid), r)`, clears `pending`, and invalidates `vkey('markups', vid)` and `vkey('bid-board', vid)`. `CarveOuts` type is in `web/src/api/types.ts`.

**Backend** (`SummaryEndpoints.cs`):
- `GET /api/versions/{id:long}/fee-carve-outs` — `Access.Version(w, id, "viewer")`; returns `CarveOuts(w, id)`, a single-row query joining `ProjectVersion` (`ApplyFeeExcludes, FeeExcludes, ExcludeGenreqFromDirect, ReservePrecon`) with the effective fee rate/off-state from `VersionMarkup`/`MarkupType`. (This GET isn't used by the frontend — the tab reads carve-outs via the price-roll-up payload instead — but it exists as the read-side counterpart of the PUT.)
- `PUT /api/versions/{id:long}/fee-carve-outs` (`CarveOutsIn { ApplyFeeExcludes, FeeExcludes, ExcludeGenreqFromDirect, ReservePrecon, FeePct }`) — `Access.Version(w, id)` (default `"editor"`, 423 if locked). Validates `FeeExcludes` only contains `genreq/precon/reserves/bond/cover` and `ReservePrecon` only contains `reserveproject/reservedesign/reserveescalation` (400 otherwise); validates `FeePct` is 0–100. `UPDATE ProjectVersion SET ApplyFeeExcludes = coalesce(...), FeeExcludes = coalesce(...), ExcludeGenreqFromDirect = coalesce(...), ReservePrecon = coalesce(...), ChangedBy = @u` (arrays are de-duplicated before writing). If `FeePct` was supplied: upserts `VersionMarkup` for `MarkupCode = 'fee'` (`ON CONFLICT ... DO UPDATE SET RatePct = @fee, FixedAmount = NULL` — this clears any fixed-amount override on the fee row) and also updates `ProjectVersion.FeePct`. Calls `Recalc.Summary(w, id, "feecarveouts.update")` (Architecture.md Recalculation engine), logs `"feecarveouts.update"`, returns the full rebuilt roll-up (`SummaryEndpoints.Build`, same shape as `GET /price-roll-up`).

**Database:** Columns on `ProjectVersion` (added in `007_fee_carveouts.sql`): `ApplyFeeExcludes boolean DEFAULT false`, `FeeExcludes text[] DEFAULT '{}'` (CHECK `FeeExcludes <@ ARRAY['genreq','precon','reserves','bond','cover']`), `ExcludeGenreqFromDirect boolean DEFAULT false`, `ReservePrecon text[] DEFAULT '{}'` (CHECK `ReservePrecon <@ ARRAY['reserveproject','reservedesign','reserveescalation']`). The fee rate itself lives in `VersionMarkup` (`MarkupCode = 'fee'`) and the denormalized `ProjectVersion.FeePct`, both touched by this endpoint when `FeePct` is sent. `TrgTouch` on `ProjectVersion` bumps `RowRev`/`ChangedAt` on every write here as elsewhere.

### Dependencies
- See `_Overview/Architecture.md`: Recalculation engine (`Recalc.Summary`, hybrid client/server `@gridline/calc` vs `Rules.Summary`), Authorization/scoping (locked-version 423).
- `04-manage-rates-and-indirect-items.md`: shares the `price-roll-up` and `markups` caches and the same `fee` `VersionMarkup` row; a fee rate change from either tab must be reflected on the other.
- Feeds the Price roll-up page's displayed fee/contract-total lines (`PriceRollUp.md`).

### Notes / edge cases
- The two CHECK constraints (`VersionFeeExcludesCheck`, `VersionReservePreconCheck`) are a second line of defense behind the endpoint's own validation — if the endpoint's allow-list (`FeeParts`/`Reserves` constants in `SummaryEndpoints.cs`) and the migration's array literals ever diverge, the DB constraint — not the C# check — is the one that will actually reject a bad value.
- Setting the fee rate via this endpoint always clears `VersionMarkup.FixedAmount` for the fee code (`FixedAmount = NULL` in the `ON CONFLICT` clause) — a fixed-amount fee override set on the Rates tab is silently discarded the next time someone saves a fee % here.
- The frontend's "fee with no carve-outs" KPI delta is computed entirely client-side via `calcSummary` as a preview and is never validated against the server's actual recalculation — if `@gridline/calc`'s rules drift from `Calc/Rules.cs`, this delta can mislead the user without an error being raised (see Architecture.md's `CalcRun` mismatch-detection, which only compares the carried calculation, not this preview).
- `carvedAmt('reserves')` on the frontend sums every roll-up line whose `code` starts with `"reserve"` — this is a client-side convention, not a server-enforced grouping; adding a new reserve-like markup code elsewhere must follow the same `reserve*` naming to show up correctly here.
- Toggling `applyFeeExcludes` to No does not clear `feeExcludes`/`reservePrecon` — they stay saved and simply stop applying, by design (explicitly called out in the UI copy), so don't "clean up" these arrays on a No toggle.
